# Go with GenAI — Домашнє завдання: Error Handling

Репозиторій-темплейт для домашнього завдання до заняття **"Error Handling: від
panic до elegant recovery"**. Структура та підхід повторюють репозиторії
попередніх занять курсу: студент дописує код у файлах з позначками `TODO`,
а GitHub Actions автоматично перевіряє виконання під час кожного push/PR.

> **Примітка щодо нумерації.** У презентації заняття домашні завдання названі
> "Завдання 0", "Завдання 1", "Завдання 2" та "Бонус". 

## Структура репозиторію

```
.
├── go.mod
├── task0_refactor/            # Завдання 0: рефакторинг у multi-package проєкт
│   ├── cmd/app/main.go        # тонкий main.go (лише wiring)
│   └── internal/
│       ├── calculator/        # calculator із Заняття 1
│       └── textanalyzer/      # text analyzer із Заняття 2
├── task1_validation/          # Завдання 1: валідатор форми реєстрації
│   ├── validator.go           # <-- допишіть TODO тут
│   └── validator_test.go
├── task2_retry/                # Завдання 2: retry-механізм
│   ├── retry.go                # <-- допишіть TODO тут
│   └── retry_test.go
└── .github/workflows/classroom.yml   # автоперевірка
```

Бонусне завдання (AI-асистоване само-рев'ю попереднього коду) не
автоперевіряється тестами 

## Що потрібно зробити

Відкрийте кожен файл, позначений `TODO`, і реалізуйте функції відповідно до
коментарів над ними:

1. **`task0_refactor/internal/calculator/calculator.go`** та
   **`task0_refactor/internal/textanalyzer/textanalyzer.go`** — перенесіть і
   доопрацюйте логіку calculator (Заняття 1) та text analyzer (Заняття 2) у
   вигляді чистих, добре протестованих пакунків з обробкою помилок через
   `errors.New` / `fmt.Errorf` + `%w`.
2. **`task1_validation/validator.go`** — власний тип `ValidationError`, що
   повертає **всі** невалідні поля форми реєстрації одночасно (не лише
   перше знайдене).
3. **`task2_retry/retry.go`** — функція `Do`, що повторює нестабільну
   операцію, розпізнає тимчасові відмови через sentinel error `ErrTemporary`
   і `errors.Is`, і повертає чітко обгорнуту фінальну помилку, якщо всі
   спроби вичерпано.

## Локальний запуск тестів

```bash
go mod download
go build ./...
go test ./... -v
```

Порада: щоб під час локального запуску теж бачити результати УСІХ тестів, а
не зупинятись на першому провалі, НЕ додавайте прапорець `-failfast` — саме
так налаштований і CI-воркфлоу.

## Як працює автоперевірка (GitHub Actions)

Workflow `.github/workflows/classroom.yml` запускається на кожен push і
pull request. Ключова властивість: **він показує в логах усі незавершені
завдання одночасно**, а не зупиняється на першій помилці, — щоб студент
одразу бачив весь обсяг роботи, що залишився:

- Кожен крок (build, Task 0, Task 1, Task 2, `go vet`) виконується з
  `continue-on-error: true`, тому провал одного завдання **не блокує**
  виконання перевірки решти завдань.
- Кожен крок тестів запускає `go test ./<task>/... -v` — вивід `-v` показує
  результат КОЖНОГО тестового випадку (включно з підтестами `t.Run`), а без
  прапорця `-failfast` виконання продовжується через усі тести пакунку,
  навіть якщо один з них провалився.
- Окремий крок "Print full logs for every task" (з `if: always()`) в кінці
  друкує повні логи всіх завдань одним блоком — зручно проглянути одразу все.
- У Job Summary (вкладка Summary запуску Action) формується короткий
  чекліст ✅/❌ по кожному завданню.
- Наприкінці окремий крок аналізує результати всіх кроків і **завершує job
  з помилкою (exit 1), якщо провалилось хоча б одне завдання** — але лише
  після того, як усі завдання вже виконались і залогувались.

Такий підхід гарантує: якщо у студента не працюють одразу Завдання 0 і
Завдання 2, у логах CI буде видно обидва провали з детальним виводом тестів,
а не лише перший.
